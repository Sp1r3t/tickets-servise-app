# Правила разработки Ticketflow

Перед любыми изменениями прочитай этот файл, `README.md`, `docs/ARCHITECTURE.md` и относящиеся к задаче ADR. При смене архитектуры обнови документацию в той же поставке. Не обещай безошибочность: показывай результаты проверок и оставшиеся ограничения.

## Назначение

Это **билетная платформа**, а не только афиша. Основной сценарий: организатор → схема зала → концерт → публикация → уникальная ссылка/iframe → выбор мест → ограниченная бронь → оплата → электронный билет → однократный вход. Сайт, будущие iOS/Android и виджет работают с одной версионированной API.

## Границы сервисов

1. Identity: пользователи, пароли, сессии, роли; будущее подключение OAuth/OIDC.
2. Catalog: принадлежащие организаторам залы, ревизии схем, концерты, публикация и неизменяемые снимки.
3. Inventory: единственный владелец доступности мест и срока бронирования.
4. Orders: заказы, долговечная saga, билеты, отметка входа и отчёт продаж.
5. Payments: состояние платежей, адаптер провайдера и компенсация платежа.

Каждый сервис запускается отдельным процессом/контейнером и владеет отдельной базой. Запрещены SQL-запросы и foreign keys между сервисами. Общий пакет содержит инфраструктуру и контракты, а не общий бизнес-слой или общую БД. Gateway маршрутизирует и ограничивает запросы; бизнес-правила остаются в сервисах.

## Инварианты

- Ни одно место нельзя продать дважды. Inventory блокирует строки мест в стабильном порядке и резервирует весь набор в одной транзакции.
- Истёкшая бронь не мешает следующей покупке даже при остановленном worker. Часы API/БД — UTC; пользователю показывается часовой пояс концерта.
- Доступ к каждому объекту проверяется по владельцу/организации. Роль из интерфейса не считается авторизацией. Чужой ID не даёт доступ.
- Деньги — целые копейки + валюта. Цены и итог берутся только с сервера. Float запрещён в расчётах денежных обязательств.
- Каждая операция, которую можно повторить после сетевого сбоя, имеет стабильный ключ и проверку совпадения параметров.
- Публикация фиксирует независимый снимок схемы и цен. Редактирование шаблона не меняет проданные места/билеты.
- Билет выдаётся только после подтверждённого платежа и успешного закрепления мест. Сбой после commit исправляется повторным идемпотентным шагом.
- Отмена и компенсация — долговечные состояния saga, а не цепочка незаписанных HTTP-вызовов. Не выпускать билет, если место уже перехвачено после истечения TTL.
- JWT для входа и для билета имеют разные audience/issuer. QR не содержит email или других персональных данных. Повторный проход запрещён транзакцией.
- Тестовая оплата явно помечена. Не объявлять реальные платежи работающими, пока нет адаптера, проверки webhook и подтверждённой компенсации.

## Изменения и проверки

- Меняй API совместимо; breaking change требует новой версии или плана миграции. Поддерживай OpenAPI и генерируемые контракты для клиентов.
- Любое изменение схемы PostgreSQL оформляй новой Alembic-миграцией. Применённые ревизии не переписывай. SQLite `create_all` — только локальная разработка.
- Обновляй Python lock и `frontend/pnpm-lock.yaml` при изменении зависимостей. Не коммить `.env`, базы, токены, логи или демонстрационные пользовательские данные.
- Для изменения бронирований, платежей, доступа или билетов нужны содержательные тесты: конкуренция, повторный запрос, чужой пользователь, истечение срока, частичный сбой.
- Перед сдачей: `ruff check services scripts tests migrations`, `pytest`, `pnpm build`; при изменении пользовательского сценария — соответствующий Playwright-тест. PostgreSQL-проверка обязательна в CI.
- Не подменяй интеграцию заглушкой без явного указания. Отличай выполненные локально проверки от подготовленных CI-проверок.
- Редактор обязан сохранять стабильные seat ID, историю действий, черновик и оптимистическую ревизию. Валидация геометрии/нумерации обязательна на сервере; ошибка сохраняет пользовательский черновик.
- Рабочая ветка по умолчанию `codex/…`. Не перезаписывай чужие изменения и не делай force push.
